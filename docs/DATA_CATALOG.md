### fct_circulating_supply_daily

NEAR's circulating supply per UTC day, built from the chain, from the day transfers were enabled. NEAR defines it as every token not subject to a lockup at that moment. This uses NEAR Explorer's formula: total supply, minus what every lockup contract still locks, minus the balances of lockup.near and contributors.near. Tested against NearBlocks' own lockup job while that ran, NEAR's published schedule, and the contracts' own answers. It does not take out the NEAR Foundation's liquid holding or the protocol treasury, and it counts staked tokens as circulating. See docs/CIRCULATING_SUPPLY.md.

- **Grain:** date_day
- **Sources:** Archival RPC lockup contract state, FastNear transfers of lockup.near and contributors.near, NearBlocks total supply
- **File:** `data/gold/fct_circulating_supply_daily.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|
| `date_day` | DATE | date | UTC calendar day, read at its close. Starts on 2020-10-13. |
| `total_supply_near` | DOUBLE | NEAR | Total supply at day end per NearBlocks, the same column as in fct_supply_daily, which a data test holds to the chain. |
| `lockup_locked_near` | DOUBLE | NEAR | Sum over all lockup contracts of the amount their schedule still locks at the day's close. A lockup whose owner never turned transfers on counts as released on schedule, as in NEAR Explorer; transfers_never_enabled_near holds those. |
| `foundation_locked_near` | DOUBLE | NEAR | Balances of lockup.near, which funds new lockups, and contributors.near, which held 418M NEAR at genesis and has since paid nearly all of it out. NEAR Explorer subtracted these two and no other account. |
| `circulating_supply_near` | DOUBLE | NEAR | total_supply_near minus lockup_locked_near minus foundation_locked_near. |
| `circulating_share_of_total` | DOUBLE | fraction | circulating_supply_near divided by total_supply_near. |

### fct_wallet_holdings

Point in time: tokens and native NEAR per tracked account, per snapshot. This cannot be backfilled, so history starts with the first snapshot. Symbol and decimals come from registry/tokens.csv where a token is listed, then from its contract's ft_metadata, which the nightly job reads for up to 2,000 tokens a night, then from the price list that prices the token (metadata_source says which). A list counts whole tokens with its own decimals, so its price and its decimals belong together, and the lists matched the contract on every token read so far; the test token_decimals_lists_match_contracts fails if that stops. A contract that has answered is final, even with an error, so no list fills in behind it. A token with none of the three keeps empty symbol, amount_token and decimals: nothing is guessed. Earlier snapshots convert too, because the latest answer for a token applies to all of them. value_usd multiplies amount_token by the price read in the same snapshot, joined on token_id from fct_token_prices, and value_status says why a row has none. Sum value_usd, not amount_token times price_usd: those rows include prices that would read $46.5B for one meme token at v2.ref-finance.near.

- **Grain:** snapshot_date, account_id, token_id
- **Sources:** FastNear /v1/account/{id}/full, registry/tokens.csv, 1Click, Rhea, RPC ft_metadata

### fct_etf_nrr_daily

A creation does not prove NEAR was bought on the market that day, because shares can be created for cash or for NEAR. Bitwise's terms limit copying its figures: see registry/sources.csv.

- **Grain:** date_day
- **Sources:** Bitwise's page, SoSoValue through news reports, archival RPC
- **File:** `data/gold/fct_etf_nrr_daily.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|

| `nav_usd` | DOUBLE | USD per share | Net asset value per share, from the chart on Bitwise's page. On a day the chart has not reached, net assets divided by shares. |
| `market_price_usd` | DOUBLE | USD per share | Closing market price per share, from the same chart. |
| `premium_discount_pct` | DOUBLE | percent | Market price above NAV, or below it if negative. |

| `fund_page_shares` | BIGINT | shares | The share count on Bitwise's page for that day, where a snapshot saw it. A data test holds shares_outstanding to it. |
| `net_assets_usd` | DOUBLE | USD | Net assets from Bitwise's page where a snapshot saw that day, otherwise shares_outstanding times nav_usd. |
| `near_in_trust` | DOUBLE | NEAR | NEAR the fund holds. Known where a snapshot saw that day, plus two dates in the history file; on 2026-09-28 it is the seed deposit seen on chain. |

| `reported_net_assets_usd` | DOUBLE | USD | Net assets reported by SoSoValue, read from a news report. A data test holds them to shares_outstanding times nav_usd. |
| `staked_share` | DOUBLE | fraction | Share of the fund's NEAR that is staked, from Bitwise's page. |
| `net_staking_rate` | DOUBLE | fraction per year | Staking reward rate after the fund's staking expenses, from Bitwise's page. |

### fct_dev_activity_weekly

Commits and active authors per tracked repository per week. A fixed repository list, not a whole-ecosystem count; GitHub's author list covers each repository's top 100. Two measures sit side by side. commits and active_authors are GitHub's own statistics: they count more than the default branch holds (about a quarter more for near/nearcore, which keeps release branches), and they come back as a year of zeros with no contributors for a repository with over 10,000 commits (anza-xyz/agave), so both are empty for a repository whose year of readings is all zero although GitHub says it was pushed to in that year. commits_default_branch and authors_default_branch are counted from the commits list with one method for every repository, so compare repositories with those.
