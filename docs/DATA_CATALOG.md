### fct_chain_daily

Chain usage per UTC day, one column per measure. Most counts come from NearBlocks /v3, which returns the last 365 days of each read, and from /v1/charts for older days: the two agree day for day wherever both exist, dq_reconciliation compares them, and /v1 is switched off on 2026-11-22. Where /v1 and /v3 count different things both are kept, under names that say what each counts: active_signers and active_accounts_with_relayed, new_contracts_v1 and new_contracts_v3. Levels of txns, receipts, active accounts, contracts, new accounts and meta columns cannot be compared across 2026-04-02: see docs/USAGE_BREAK_2026-04-02.md.

- **Grain:** date_day
- **Sources:** NearBlocks /v3/txn-stats, /v3/address-stats and /v3/block-stats, and /v1/charts for days before their window
- **File:** `data/gold/fct_chain_daily.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|
| `date_day` | DATE | date | UTC calendar day. |
| `txns` | BIGINT | count | Transactions: /v3/txn-stats, else /v1/charts for older days. The two agree on every day both hold. |
| `meta_txns` | BIGINT | count | Meta-transactions, where a relayer pays gas for the user. |
| `meta_txn_share` | DOUBLE | fraction | meta_txns divided by txns. |
| `receipts` | BIGINT | count | Receipts. |
| `blocks` | BIGINT | count | Blocks: /v3/block-stats, else /v1/charts. |
| `chunks` | BIGINT | count | Chunks across all shards. Last 365 days of reads only. |
| `shards` | INTEGER | count | Shards that day. Last 365 days of reads only. |
| `gas_price_yocto` | DOUBLE | yoctoNEAR per gas | Gas price per NearBlocks /v3/block-stats. Last 365 days of reads only. It has sat at the protocol's minimum all year; dim_block_day holds the price in one block a day. |
| `active_signers` | BIGINT | count | Active accounts per /v1/charts. NearBlocks does not document it, but it matches Nansen's published distinct signers, so it leaves out users whose transactions a relayer signs. Ends on 2026-11-22, when /v1 is switched off. |
| `active_accounts_with_relayed` | BIGINT | count | Active accounts per /v3/address-stats. NearBlocks does not document it, but it stays within 2% of active_signers plus meta_accounts, so it also counts users whose transactions a relayer signs. ### fct_wallet_holdings

Point in time: tokens and native NEAR per tracked account, per snapshot. This cannot be backfilled, so history starts with the first snapshot. Symbol and decimals come from registry/tokens.csv where a token is listed, then from its contract's ft_metadata, which the nightly job reads for up to 2,000 tokens a night, then from the price list that prices the token (metadata_source says which). A list counts whole tokens with its own decimals, so its price and its decimals belong together, and the lists matched the contract on every token read so far; the test token_decimals_lists_match_contracts fails if that stops. A contract that has answered is final, even with an error, so no list fills in behind it. A token with none of the three keeps empty symbol, amount_token and decimals: nothing is guessed. Earlier snapshots convert too, because the latest answer for a token applies to all of them. value_usd multiplies amount_token by the price read in the same snapshot, joined on token_id from fct_token_prices, which holds the price itself, and value_status says why a row has none. Sum value_usd, never amount_token times a list price: those prices include one that would read $46.5B for one meme token at v2.ref-finance.near. Native NEAR is the RPC view_account balance read the same night where there is one, because FastNear's account state for treasury.near read 47.76 NEAR on every snapshot while the account held about 1.59M.

### fct_defi_tvl_daily

### dq_freshness

How current each dataset is, relative to the newest snapshot the build can see, and whether that is too old. Covers the daily series and the datasets read as a snapshot each night. A dataset that falls further behind than its limit is stale, and the data test no_dataset_is_stale then fails, so a source that stops arriving is noticed.

- **Grain:** model
- **Sources:** silver tables
- **File:** `data/gold/dq_freshness.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|
| `dataset` | VARCHAR | text | Readable dataset name. |
| `model` | VARCHAR | text | Silver model name. |
| `cadence` | VARCHAR | text | daily for a series with one value per day, snapshot for a dataset that holds only what was read each night. |
| `latest_snapshot` | DATE | date | Newest snapshot holding this dataset. |
| `latest_data_day` | DATE | date | Newest day of data. For a snapshot dataset, the day of its newest read. |
| `as_of` | DATE | date | Newest snapshot across all datasets. |
| `days_behind` | BIGINT | days | Days between latest_data_day and as_of. A daily series normally reads 1, because the newest full day is yesterday. |
| `max_days_behind` | INTEGER | days | The most days this dataset may fall behind before it counts as stale: 3 for a daily series and 2 for a snapshot, which leaves room for one missed night, 7 for the Bitwise fund, which trades on weekdays and fills its chart a day late, and 35 for the Intents pool's chain readings, which are taken at month ends. Empty where no limit applies: a reading taken by hand, and NearBlocks' legacy charts, which are switched off on 2026-11-22. |
| `is_stale` | BOOLEAN | boolean | True when days_behind is over max_days_behind. Always false where there is no limit. |
| `rows_all_snapshots` | BIGINT | count | Rows across all snapshots. |

### dq_bigquery_reads
