### fct_supply_daily

Supply and implied issuance per UTC day. Epochs end at uneven times, so one day's minted_near is lumpy; use averages of 30 days or more. Circulating supply is in fct_circulating_supply_daily, and gas fees are in fct_chain_daily.

- **Grain:** date_day
- **Sources:** NearBlocks /v3/block-stats and /v1/charts, FastNear transfers of treasury.near, protocol config
- **File:** `data/gold/fct_supply_daily.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|
| `date_day` | DATE | date | UTC calendar day. |
| `total_supply_near` | DOUBLE | NEAR | Total supply at day end per NearBlocks: /v3/block-stats, else /v1/charts for older days. It equals the chain's own supply in the first block of the next day on every day the archival node was read, which a data test holds. |
| `supply_change_near` | DOUBLE | NEAR | Change in total supply from the previous day. |
| `contract_gas_reward_rate` | DOUBLE | fraction | Share of function-call gas paid to the called contract on that day (the developer gas rebate): the newest protocol config read on or before the day, and the first read's 0.3 before 2026-10-28. A change that registry/protocol_upgrades.csv dates to the block holds from the next day, and its own day takes both rates weighted by the time each was in force, as if gas were spread evenly over the day: 0.147 on 2026-11-04, when protocol version 87 set the share to 0 at 11:46:29 UTC. |
| `burn_near` | DOUBLE | NEAR | Gas fees (fct_chain_daily.gas_fee_near) times one minus contract_gas_reward_rate. The rebate came only out of gas burnt executing function calls, so before protocol version 87 the real burn was more than 70% of gas and this is a lower bound; the upper bound is the whole fee, fct_chain_daily.gas_fee_near. The burn can be read straight off the chain only before issuance began on 2020-10-20, when every fall in supply was gas burned: over those 79 days supply fell by 84.8% of gas fees, 124.4 NEAR against this column's 102.7, and the lower bound held on every one of them, which a data test keeps. That share belongs to 2020's mix of transactions and is not applied to later years. From 11:46:29 UTC on 2026-11-04 all gas burns; that day itself is the time-weighted mix. |
| `treasury_reward_near` | DOUBLE | NEAR | EpochRewards received by treasury.near that day, from wallet transfers. Part of minted_near, not on top of it. |
| `minted_near` | DOUBLE | NEAR | supply_change_near plus burn_near: issuance implied by the chain. It inherits burn_near's lower bound, so before 2026-11-04 the real figure is higher by up to 30% of that day's gas fee, which is small against issuance: 3.36M NEAR of modelled burn against 314.5M minted through 2026-11-08. |
| `minted_annualized_rate` | DOUBLE | fraction per year | minted_near times 365, divided by total supply. Noisy for a single day. |

### fct_circulating_supply_daily

NEAR's circulating supply per UTC day, built from the chain, from the day transfers were enabled. NEAR defines it as every token not subject to a lockup at that moment. This uses NEAR Explorer's formula: total supply, minus what every lockup contract still locks, minus the balances of lockup.near and contributors.near. Tested against NearBlocks' own lockup job while that ran, NEAR's published schedule, and the contracts' own answers. It does not take out the NEAR Foundation's liquid holding or the protocol treasury, and it counts staked tokens as circulating. See docs/CIRCULATING_SUPPLY.md.

- **Grain:** date_day
- **Sources:** Archival RPC lockup contract state, FastNear transfers of lockup.near and contributors.near, total supply from fct_supply_daily
- **File:** `data/gold/fct_circulating_supply_daily.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|
| `date_day` | DATE | date | UTC calendar day, read at its close. Starts on 2020-10-13. |

### fct_wallet_holdings

Point in time: tokens and native NEAR per tracked account, per snapshot. This cannot be backfilled, so history starts with the first snapshot. Symbol and decimals come from registry/tokens.csv where a token is listed, then from its contract's ft_metadata, which the nightly job reads for up to 2,000 tokens a night, then from the price list that prices the token (metadata_source says which). A list counts whole tokens with its own decimals, so its price and its decimals belong together, and the lists matched the contract on every token read so far; the test token_decimals_lists_match_contracts fails if that stops. A contract that has answered is final, even with an error, so no list fills in behind it. A token with none of the three keeps empty symbol, amount_token and decimals: nothing is guessed. Earlier snapshots convert too, because the latest answer for a token applies to all of them. value_usd multiplies amount_token by the price read in the same snapshot, joined on token_id from fct_token_prices, which holds the price itself, and value_status says why a row has none. Sum value_usd, never amount_token times a list price: those prices include one that would read $46.5B for one meme token at v2.ref-finance.near. Native NEAR is the RPC view_account balance read the same night where there is one, because FastNear's account state for treasury.near read 47.76 NEAR on every snapshot while the account held about 1.59M.

- **Grain:** snapshot_date, account_id, token_id
- **Sources:** FastNear /v1/account/{id}/full, RPC view_account, registry/tokens.csv, 1Click, Rhea, RPC ft_metadata
- **File:** `data/gold/fct_wallet_holdings.parquet`

| Column | Type | Unit | Description |
|---|---|---|---|
| `snapshot_date` | DATE | date | Date the source was read. |
| `account_id` | VARCHAR | account id | NEAR account. |
| `token_id` | VARCHAR | token id | Token contract, or Intents asset id. |
| `symbol` | VARCHAR | text | Token symbol. Where metadata_source is ft_metadata or price_list this is the contract's or the list's own claim, so a token calling itself USDC need not be USDC. Group by token_id, and treat this as untrusted text when displaying it. |
| `balance_raw` | VARCHAR | raw units | Balance in the token's smallest unit, as a string so no digits are lost. |
| `amount_token` | DOUBLE | token units | Amount in whole tokens: balance_raw over 10 to the power of decimals, as a double. Empty where decimals are unknown. Where metadata_source is ft_metadata the decimals are the contract's own claim too. |

### fct_token_prices
